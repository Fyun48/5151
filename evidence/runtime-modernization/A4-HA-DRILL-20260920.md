## 2. Manual failover drill（A → B → 交回 A）

時間皆為 UTC（主機 `date -u`）。

| # | 動作 | 指令（在當下 primary 執行） | 時間 / 結果 |
|---|---|---|---|
| 1 | 種 marker 並確認已複製 | `INSERT INTO drill_marker VALUES (1)`；A/B `count=1`、LSN 皆 `0/4495C60` | **RPO 基準：lag = 0** ✅ |
| 2 | fence 舊 primary | CasaOS `docker stop 5151-postgres-A` | `03:23:17Z`，`Exited (0)` ✅ |
| 3 | 確認舊 primary 真的不可用 | B → `psql -h 192.168.0.140 -p 15432` | `Connection refused`（exit 2）✅ |

### RPO / RTO 實測

| 指標 | 結果 |

| RPO | **0**（fence 前 marker 已複製；兩次 failover 後 marker 1–4 全數保留，row count 一致）|

## 3. 驗收（repo 既有腳本）

```
=== verify-primary.sh（CasaOS）===
192.168.0.220|streaming|async      ← standby 有在串流
primary count = 1                  ← 可寫

=== verify-standby.sh（Synology）===
pg_is_in_recovery() = t            ← 只讀
standby count = 1                  ← 與 primary 一致
write on standby → ERROR: cannot execute INSERT in a read-only transaction   ← split-brain 防護 ✅
```

最終狀態：A = primary（`pg_stat_replication` = `192.168.0.220｜streaming`、slot `standby_b` active）、
B = standby（`t`、replay LSN 追平）；shadow 其餘容器（web-A/B、haproxy、cloudflared-A/B、crawler、worker）
全程未重啟、狀態不變 ✅。

## 4. 演練抓到的真問題（全部已修進 repo）

| # | 問題 | 症狀（實測） | 修正 |

| D1 | `restore.sh` DB 名未加引號 | `DROP DATABASE IF EXISTS 5151_restore_test` → `trailing junk after numeric literal`；**還原演練從來沒成功過** | 識別字加雙引號 + 名稱白名單 |

| D4 | pg_hba 只有 LAN 網段 | 從 peer 主機的容器做 `pg_basebackup` → `no pg_hba.conf entry for replication connection from host "172.21.0.1"`（docker-proxy 讓來源變 bridge gateway） | `fix-pg-hba.sh` 支援 `REPL_CIDRS`（預設 `192.168.0.0/24 172.16.0.0/12`），仍要求 scram 密碼 |

| D7 | runbook 的 rejoin 步驟不完整 | 沒說要（a）在新 primary 為被重建節點建 slot、（b）要掛**被重建節點自己的 volume**（standby compose 掛的是 `5151-shadow-pg-b`）| runbook §8 改寫；`setup-standby.sh` 支援 `PRIMARY_HOST`/`PRIMARY_PORT`/`SLOT_NAME` |

### 憑證落差（本次**未變更任何密碼**，僅記錄）

- live `5151-postgres-A` 的 env `POSTGRES_PASSWORD` 是一串**被黏在一起的**值
  （本檔原本寫出那串值的前後各 3 碼；**2026-09-21 已移除**，完整值見 workspace 的
  `INFRA-CREDENTIALS.md`，不在 repo 內）→ 產生 env 時吃掉了換行。
  實測：筆記載的超級使用者密碼在 TCP（非 loopback）上**驗證失敗**，實際可用的是那串黏起來的值。
- replication 真實密碼可由 standby 的 `primary_conninfo` 取得（本次靠它完成 rejoin；值記在本機筆記，不進 repo）。
- 建議：下次重建 shadow pg-A 時直接用 repo 的 `postgres-primary/docker-compose.yml`（乾淨的
  `${PG_SUPER_PASSWORD}`），讓 live 與文件一致；在那之前以實測值為準。

### 4.1 已解決（2026-09-20 06:45–06:48Z，Owner 指示「重建 shadow `5151-postgres-A` 消憑證落差」）

落差比原記錄更深 —— 實際有 **三處**與文件不符：

| 位置 | 原本 | 處理 |
|---|---|---|
| CasaOS `postgres-primary/.env` | 兩個各 24 字元的**錯值**（非文件值） | 改寫成文件值 `PG_SUPER_PASSWORD` / `PG_REPLICATION_PASSWORD`（值見 workspace 的 `INFRA-CREDENTIALS.md`，**不在 repo 內**）（舊檔保留為 `.env.bak-20260920T064533Z`）|
| primary 的 `replicator` 角色 | 密碼與文件不符 → `pg_basebackup` 得到 `password authentication failed` | `ALTER ROLE replicator WITH LOGIN REPLICATION PASSWORD '<文件值>'` → TCP 登入成功 |
| primary 的 `postgres`（super） | **文件值（13 字元）與舊 .env 值（24 字元）都登不進去** | `ALTER ROLE postgres WITH PASSWORD '<文件值>'` → `super_tcp_ok` |

- 安全性判斷：shadow web 容器只有 `DB_DRIVER` / `DATA_DIR`，**完全沒有 Postgres 密碼**（v3 仍走 SQLite），
  且改密碼時 standby 已 fence 停機 → 不影響任何消費者。
- 重建流程（＝runbook §8 rejoin 實走一次）：CasaOS `docker compose stop 5151-postgres-A`
  → `--profile setup run --rm standby-basebackup`（38,483 kB、`standby.signal` + `primary_conninfo` 寫入）
  → `docker compose up -d` → log：`consistent recovery state reached` +
  `started streaming WAL from primary at 0/E000000 on timeline 4`。
- 驗證：standby `pg_is_in_recovery()=t`、receive=replay（`0/E000060` → 後續 `0/E0161C0`）；
  primary `pg_stat_replication` = `172.21.0.1|streaming|async|0/E0161C0|0/E0161C0`；
  在 primary 建 `rejoin_probe` 並 INSERT → standby `count=1`（端到端複寫）；
  **HAProxy 全路徑** `25433 → pg_is_in_recovery()=f`（正確導向 primary）。
- 附帶修掉：`postgres-primary/docker-compose.yml` 的 `PRIMARY_HOST` 由 `${SYNOLOGY_HOST:?...}` 改成
  `${SYNOLOGY_HOST:-192.168.0.220}`（peer compose 同理）—— compose 會插值整個檔案，舊寫法會讓
  **不帶變數的 `docker compose up -d` 直接失敗**（本次實測踩到）。
