# PR-A 入口 × 資料對照表（2026-09-27）

## 這份是什麼、為什麼現在才有

`pr-a-access-matrix-20260924.md` 的入口清單**早就機械抽取了 288 條路由**，但那份矩陣
**只填了 2 條**，其餘寫著「C. 尚未確認（不填 PASS；需逐入口追）」。

**那一步沒做完就往下改架構**，就是後來所有來回的根源：搬了一半、另一半還在各節點 SQLite，
於是出現「同一頁兩台顯示不同」「管理員改了只有一台生效」。

這份把那個洞補起來：**288 條全部**，每條標明用到哪些表、走 SQLite 還是 PG、以及證據等級。

## 怎麼產生（可重跑）

```
node v3/scripts/route-data-map.mjs
```

1. 載入 `v3/src/*.js` 與 `v3/src/repository/*.js`，解析每個檔的 import 與頂層函式。
2. 由 `db.js` 算出「只走 SQLite」的函式集合（直接碰 `db.prepare`/`exec` 且本文無 driver 判斷，
   再沿呼叫鏈傳遞）。
3. 建 **(檔, 函式)** 節點與跨模組呼叫邊，做 fixpoint，得出每條路由可達的 SQLite／PG 函式。
4. 表名同樣沿呼叫鏈傳遞（`getHousingData()` 本身沒有 SQL，SQL 在它呼叫的 `settingKey()` 裡）。

### 開發過程中修掉的三個誤判（方法論上的教訓）

| 症狀 | 原因 | 修法 |
|---|---|---|
| 207 條被判 SQLite（過多） | 把「任何從 db.js 匯入的函式」都算成 SQLite，含純輔助 | 只認真的會碰 SQLite 的函式 |
| `/api/state` 被判 SQLite | 它透過 `loadListingPage`（別的模組）走 PG，而我只追 server.js 本地 | 改成**跨模組**呼叫圖 |
| `/api/member-mail` 被判 MIXED | 我追進 `*Async.js` 內部，把它自己的 SQLite 分支算成該路由在用 SQLite | **不展開 `*Async.js` 內部**：那是同一個函式的替代分支 |

### 仍存在的限制（據此動手前仍須人工確認）

- 動態組字串的 SQL、`db["x"]` 這類取用抓不到。
- 同名遮蔽、匿名回呼內的呼叫不追。
- 路由本文以「到下一個行首 `});`」近似。
- 標 **MIXED** 的列代表「兩邊都到得了」，**不一定**是壞事（可能只是同一條路由內不同段落各走一邊），
  需人工看哪一段走哪邊。

## 步驟 2：PG schema 已完整對應 SQLite（2026-09-27）

把兩邊的 schema 全量比對（CasaOS `591-tracker-v3:/data/v3.db` 對生產 PG `5151_shadow`）：

| | 表數 | 欄位數 |
|---|---:|---:|
| PostgreSQL | 102 | 1,018 |
| SQLite | 98 | 997 |
| **SQLite 有、PG 沒有** | **0 張** | |
| **兩邊都有但欄位不同** | **0 張** | |

PG 多出來的 4 張表：`drill_marker`、`job_queue`、`rejoin_probe`、`repl_test`
（名稱看起來是 HA 演練／複寫測試留下的，不是缺口）。

**結論：schema 不是問題，也不需要補。** 98 張表、997 個欄位在 PG 全部存在，且欄位集合完全相同。
所以後續工作純粹是「把還在 SQLite 的路由切過去」，不涉及資料庫結構變更。

這也讓步驟 3 的風險降低：不需要 migration、不需要 `ALTER TABLE`、不會有欄位對不上的情況。
