# OPS／多站藍圖（完整、雙向、不打死結）

給 Owner 讀的總稿。短表在 [`PLAN.md`](PLAN.md)，現況對照在 [`INVENTORY.md`](INVENTORY.md)，v3 外掛在 [`../v3/PLAN-integrations.md`](../v3/PLAN-integrations.md)。

**理想只有一句：每個公開站沒有 OPS 也能營業；OPS 沒有某一個站也能活。兩邊是訂閱，不是器官移植。**

本檔已依 2026-09-10 ChatGPT 審查修訂。構想可做，但在下列契約落地前，**不宣稱**「多站已隔離、退出即可交接、每種操作都可恢復、預算絕不超支」。

Owner 直接下令改程式並部署，永遠不必走這條線。

---

## 0. 三個不可退讓的原則

1. **各站獨立營運。** 登入、帳號復原、會員、營業方案、回饋、附件、站內 CRM 都不能讀 OPS 才成功。
2. **OPS 可訂閱可退出。** 退出不是整站搬家；暫停、解除訂閱、移交、刪複本是四件不同的事。
3. **Owner 直接指令不被 OPS 卡住。** 「改程式並合併／部署」就是該次操作授權。不得要求再到 OPS 投票、重按 Gate、補建任務或等待 OPS 恢復。

---

## 1. 我想做成什麼

不是「一個神站管死所有站」，而是一座**可掛、可卸的工作臺**：

- 吉比租房、你自己的下一站、幫別人做還在營利的站，都可以掛上來看回饋、評估、做版本、抽去識別洞察。
- 任何一站都可以卸下來：對方帶走自己的程式、資料庫、意見箱、站內 CRM、外掛金鑰。你的 OPS 少一張產品卡，其它站不受影響。
- 付費外掛、製作 AI、測試站、自動上正式機，全部可開可關。關了就回到已在跑的免費／手動路徑。
- 每一塊都要能裝上也能拆掉。拆掉之後行為等於加入前，或等於該包寫明的基準 SHA。

## 2. Owner 授權契約

| 任務來源 | 實際路徑 | OPS 不在線時 |
| --- | --- | --- |
| 使用者回饋觸發的 OPS 自主任務 | 分析 → Gate #1 → 製作與測試 → Gate #2 → 既有 Deploy | 自動化等待或暫停；公開站繼續營運 |
| Owner 直接交代改碼並部署 | 完成修改、必要驗證及已授權合併 → Build／Predeploy／Deploy，`manual_owner` | 照樣執行；紀錄可事後匯入 OPS |
| Owner 想從 OPS 介面啟動直接任務 | 介面保存同一份 Owner 指令與範圍，走直達路徑 | 仍保有不經 OPS 的 workflow 入口 |

來源與授權必須來自**已驗證身分與任務紀錄**。AI 不得只在 payload 寫 `owner_direct=true` 就冒充 Owner。

兩條路徑共用部署執行層的版本驗證、互斥、備份／相容性檢查；這些檢查不能依賴 OPS 在線。同一站不能同時被兩次部署改寫。Owner 直達完成後，OPS 舊候選必須重新比對實際正式版本，不能把新版本蓋回去。OPS 顯示「未知」時，直達路徑可自行核對 GitHub run 與目標站狀態。

只要求審查、規劃或改碼的指令，依實際範圍處理，不自行擴張成部署授權。本次藍圖修訂**不是**部署指令。

## 3. 兩層世界

```
                    你的 OPS（控制臺）
                    ops.db / 5151-ops / jibbyrentops
                   ↑ 訂閱複本、指標、議題      ↓ 只觸發「已存在的部署按鈕」
                   │ 絕不當對方的主資料庫      │ 絕不 SSH 進對方營業庫亂寫
  ┌────────────────┼───────────────────────────┼────────────────┐
  │ 站 A 吉比租房   │ 站 B 你的下一站            │ 站 C 幫別人做的營利站 │
  │ 自己的容器/庫   │ 自己的容器/庫              │ 自己的容器/庫         │
  │ 意見箱在本機    │ 意見箱在本機               │ 意見箱在本機          │
  │ 外掛金鑰在本機  │ 主題色在本機               │ CRM 本體在本機        │
  └────────────────┴───────────────────────────┴────────────────┘
```

**運行時單向：** 站 → OPS（抄回饋、可選抄指標）。OPS 不在對方頁面渲染路徑上。  
**治理時有限回寫：** 只有 Gate #2 同意後，OPS 去按該站已經存在、受保護的 Deploy。Owner 直達不經這個門。  
**分家時反向：** OPS → 匯出包給對方，然後停訂閱。不是對方站來跟 OPS 要資料才能開張。

現有「同一 repo、同一條 Tunnel」只約束**目前這幾個站的維護**。客戶移交到獨立 repo／主機是另有範圍的移轉能力，不是現在就把 monorepo 拆掉。

## 4. 多站身分（第 1 包必須先完成）

產品至少具備：穩定的 `product_id`、經營者、來源實例、訂閱狀態與**訂閱世代**、功能權限，以及各環境的 repo／workflow／container／資料位置／部署身分綁定。

顯示名稱、repo 子目錄、workflow 名稱**都不能**當唯一安全識別。

- 憑證驗證後由**伺服器**決定 `product_id`。站端在 body 自填的 product 只當日誌，不能改歸屬。
- 回饋事件、附件、CRM 複本、議題、AI job、通知、預算、匯出、刪除與部署紀錄都必須可追溯至正確站台。
- 既有單站資料以 Migration **明確歸入 `v3`**，不允許無法辨識的資料自動歸入「目前選取站」。
- 事件去重：`(product_id, event_id)`。來源資料另用 `(product_id, source_instance_id, source_record_id, event_type, source_version)`。重試保留同一 event_id。
- 訂閱世代負責拒絕舊授權。換世代不能讓相同歷史資料變成新資料。
- 每站／每環境各有穩定版本、發布候選、執行互斥與可用部署目標。
- 站 C 的帳號、憑證與任務不能查詢、匯出、花掉站 A 的預算或部署 A。查單筆 ID、背景 worker、批次匯出都要驗證，不能只在列表加 filter。
- 可共享程式碼；執行時不能共用可混寫的資料庫、全域客服名單或同一把外包商部署憑證。

### 4.1 第 1 包資料模型

| 表 | 責任 |
| --- | --- |
| `ops_product` | `id`、顯示名、`status`（active／paused／exiting／exited） |
| `product_subscription` | 每站一列：`generation`、訂閱狀態、能力 JSON、起訖 |
| `product_ingest_credential` | HMAC 密鑰（API 不回傳）、世代、active／revoked |
| `ingested_feedback.product_id` | 去重改 `(product_id, delivery_id)`、`(product_id, idempotency_key)` |
| `production_stable_current` | `(product_id, environment_key)`；含 static_tree_hash／schema_compat |
| `product_environment_binding` | 每站／每環境的 repo／workflow／container／資料位置／部署身分；顯示名不能當鍵 |
| `production_release_target_lease` | 每站／每環境部署互斥 |
| `instruction_record` | 已驗證 session／workflow actor 的指令紀錄（append-only） |

### 4.2 訂閱生命週期

| 狀態 | 可做 | 進行中的工作 | 失敗恢復 |
| --- | --- | --- | --- |
| 連接中 | 發憑證、測通 | 尚未收事件 | 取消連接；憑證可撤 |
| 已連接 | 收允許的事件；本站可停送 | 依能力 | 暫停或退出 |
| 暫停 | 重啟、退出 | 新自動任務停；已送出的外部呼叫不宣稱撤銷 | 重啟後只收新事件 |
| 退出中 | 看未決清單、匯出 | 停新授權；確認未決部署／扣費 | 可重試退出紀錄 |
| 已退出 | 重新連接（新世代） | 無新操作 | 產品卡留最小摘要，不刪卡 |
| 重新連接 | 發新憑證 | 預設不補送退出期間資料 | 舊憑證不得復活 |

刪除 OPS 複本是**另一個工作狀態**，不和訂閱狀態混成單一開關。

## 5. 把「退出」拆成四種動作

「解除 OPS 訂閱」與「把整站搬到對方機器」是兩項獨立能力。單純停訂閱，站台可以留在原本代管環境。

| 畫面動作 | 使用者看得懂的效果 | 資料效果 | 恢復方式 |
| --- | --- | --- | --- |
| 暫停某項功能 | 暫停 AI 分析、製作或指標傳送；本機營業繼續 | 訂閱能力關閉；憑證可留 | 重新啟用；說明待處理工作是否繼續 |
| 解除 OPS 訂閱 | 停止本站向 OPS 傳送；撤銷 OPS 對本站的新操作權限 | 撤銷該世代憑證；本機主本保留 | 新憑證、新世代；預設只處理重新加入後的新事件 |
| 移交整站 | 匯出並驗證程式、資料及附件；移交帳號與部署能力 | 見第 6 節交接包 | 依移轉階段切回；正式切換後確認唯一寫入端 |
| 刪除 OPS 複本 | 清除明列範圍的複本與衍生可識別資料 | 本站主本保留；稽核留最小摘要 | 清除不是暫停；能再匯入的範圍取決於來源與授權 |

站內後台必須有「停止傳送至 OPS」，在 OPS 當機、帳號無法登入或雙方終止合作時仍可操作。介面要顯示本機設定是否已生效。解除 OPS 不代表取消代理商、LLM 或其它外部服務的月租。

若另售付費 OPS 服務，欠費／到期只能停該服務；網站自身向顧客收費的訂閱與會員權益由本站維護。

### 5.1 退出中的一致性

1. 建立可重試的退出紀錄，停止接受本站新的自動任務與部署授權。
2. 本站停遞送；OPS 撤銷該次訂閱憑證。OPS 無法聯絡本站時，必須顯示「OPS 權限已撤銷，本站停止遞送尚未確認」。
3. 列出已排程、已認領、已送出至供應商或 GitHub 的工作。尚未送出的可取消；已受理的部署／扣費不能宣稱按取消就撤銷。
4. 每個 worker 在發出外部操作及套用結果前，重驗訂閱世代與權限。晚到的分析、webhook、舊 AI 結果不能重新開單、寫入新結果或恢復已取消訂閱。
5. 正式部署狀態不明時，先確認該環境實際結果，再完成移交。
6. 完成匯出／可選清除後標示已退出。產品卡保留最小歷史摘要與「重新連接」。

重新加入預設不補送退出期間資料。舊憑證、舊佇列不得因重新加入自動復活。

### 5.2 outbox 與附件

回饋＋初始 outbox 的原子寫入應保留。長期停用時，初始紀錄可成為精簡的本機稽核／不遞送紀錄，不應無限保留完整傳輸 payload。優先清理傳輸複本，保留 feedback 主本。

截圖、語音、附件 metadata 必須有站內主本或站方持有的儲存。文字在本機、附件只在 OPS，不算可獨立營運。附件可非同步鏡像，不能把複製成功當作送出回饋的前提。

## 6. 移交整站的完成條件

第 3 包要交的是「可驗證的交接包」，不是退出清單。至少：

| 類別 | 必須包含或處理 |
| --- | --- |
| 可建置程式 | 該站程式、runtime 共用模組、package／lockfile、Node 版本、Dockerfile／Compose、Migration、靜態資產、授權與說明 |
| 營運資料 | 一致時間點的 DB 備份、本機回饋、CRM、上傳檔及 metadata；檔案清單、雜湊、schema 版本 |
| 啟動與帳號 | 獨立管理員登入與復原、env 模板、排程、寄信、通知、第三方 callback、金流 webhook |
| 基礎設施 | 網域／DNS／TLS／Tunnel、儲存、備份還原、registry／CI、監控告警的經營者 |
| 外部服務 | 外掛帳號、金鑰與付費責任；對方自有者移交，原本共用者改對方自己的憑證 |
| 權限撤回 | 訂閱憑證以外：GitHub App／deploy key、registry、webhook、SSH、Cloudflare、OAuth、客服帳號 |

先在乾淨環境還原，封鎖對 OPS 與原 Owner 私有基礎設施的連線，驗證可建置、啟動、登入、收回饋、看附件、操作 CRM、核心排程、備份及自行部署。

對外營業有持續寫入時，規劃短暫停寫或最後差異同步，確認只有一個有效寫入端，再切換流量。

分家不一律匯出 API Key。資料庫密文需要站方獨立可用的解密方式，或交接時重新加密／換憑證。不可附帶 Owner 的跨站金鑰或其它客戶資料。

共用設計元件必須在 build 時打包、使用固定套件版本，或連同快照授權交付。分家站不可在 runtime 回原 OPS 抓 tokens／JS／登入設定。

## 7. CRM：四欄不能混成一個「狀態」

| 資料 | 主本及可編輯位置 | OPS 上的呈現 |
| --- | --- | --- |
| 站方客戶／名單／客服往來 | 站內 CRM；客戶不一定有會員帳號 | 訂閱允許的欄位複本，顯示來源與最後同步時間 |
| 站方回饋處理狀態 | 站內 feedback／客服案件 | 「站方處理進度」；更新由站方事件傳入 |
| 開發需求、評估、發行進度 | OPS 的議題與任務 | 「OPS 開發進度」，與站方客服進度分開 |
| Owner 對合作公司的商務備註 | OPS 自己的 CRM 資料 | 按歸屬與移交範圍處理，不能假稱是站方複本 |

一則意見可以同時是「站方已回覆顧客」與「OPS 尚未開發」。第一版提供「前往本站處理」、來源連結、同步時間與延遲提示。

若要在 OPS 直接回覆客戶：另加預設關閉的「遠端客服操作」。OPS 提交具權限、版本與去重識別的命令，**本站驗證後由本站服務寫本機**，再回報結果。本站不在線就排隊／失敗，不能假裝已回覆成功。

第一版 CRM：聯絡人／公司、來源回饋、案件、備註、指派、標籤與待辦。不要把只有聯絡人複本的畫面稱作完整 CRM。

**關閉 CRM＝停用介面與新處理、保留既有資料。** `DROP` 不是反悔方式；資料清除是另一個明確動作。

## 8. 跨站洞察與清除

授權拆為：回饋複製、CRM 欄位同步、統計指標、跨站分析、後續服務使用、退出後保留。回饋權限不自動包含會員名單或行銷用途。

產品卡保存站方同意的用途、範圍、有效期間與撤回紀錄。這份系統設定不能代替實際適用的告知與契約。

不把「去掉 email／電話」當作完成匿名化。沒有另外約定的退出後用途，預設停止用該站複本產生新洞察。

清除清單須涵蓋複本、附件、搜尋索引、向量、AI 摘要、衍生名單、快取、待重試 payload 與匯出副本。備份還原時重新套用清除／撤回紀錄，避免被刪資料或舊訂閱復活。

## 9. 任務、取消、退回

雙向驗收重點是「每個階段有合理的下一步、能停止不想做的工作、能修正錯誤」，不要求已發生的外部事件可以抹除。

- 前期可撤回／暫緩／拒絕；被封鎖的議題只有 Owner 可解除。
- 製作／測試中的取消要有取消要求與結果確認，並處理已建立的 branch、PR、staging、排程與供應商工作。
- 正式部署已受理時，顯示執行中與已知結果。取消排程、取消 runner、程式退回、DB 還原是不同操作。
- **已發布工作維持完成事實。** 退回另記發行事件。再次開發建立 linked follow-up／revision，不重用已發布的開發執行與授權。`RELEASED → ROLLED_BACK → EVALUATING` 的間接循環要拿掉（第 5 包）。
- Gate #2 除同意／拒絕，應有「要求修改」與文字說明。已授權 Owner 直達任務不經這個門。
- 測試站 TTL 到期要顯示已到期，可重建相同版本。一站共用一個 staging 時，要防止 A 候選的連結其實已被 B 覆蓋。

版本退回應記錄 source SHA、image digest、程式／靜態資產版本、Compose／設定版本、schema 相容範圍與上一個可用版本。現行 bind-mount 要還原對應檔案；舊程式若讀不了新 schema，就不能宣稱直接換映像可救回。

## 10. 預算與外掛（v3 站內）

細節在 [`../v3/PLAN-integrations.md`](../v3/PLAN-integrations.md)。這裡只鎖契約：

- `daily_budget_twd = 0`＝不准花錢，不是無限。
- **已結算＋保留中＋本次上界 ≤ 上限。** 短交易保留後才打外網。timeout 不釋放已送出額度。
- 金額用整數最小單位，不用 float。
- 初始全部付費功能關閉、日／月預算 0。
- 關開關＝該包寫明的基準 SHA 行為；不會自動撤銷已扣費呼叫、已發出部署、已採用的 AI 結果或既有 CRM 資料。

## 11. 工作包（依 ChatGPT 調整後的順序）

每包完成的是「可驗證成果」，不是日曆。並非每包完成就能宣稱全產品可獨立營運；要區分可部署、可啟用、可移交。

Owner 直達部署從現在就保留，不必等第 8 包。OPS 新工作流是部署 **OPS 自身**，不能變成 v3 的第四條替代部署路徑。

### 包 10 — 遠端客服操作

- OPS 提交具權限、版本與去重識別的命令；本站驗證後由本站寫本機，再回報。
- 本站不在線就排隊／失敗，不能假裝已回覆成功。
- 反悔：`remote_cs=0`、`OPS_REMOTE_CS_DELIVERY=0`、`V3_OPS_COMMAND_ACCEPT=0`；已寫入的本機處理保留。

### 包 11 — 跨站洞察與清除

- 授權拆開：回饋複製 ≠ 跨站分析 ≠ 退出後保留。預設後兩者關。
- 沒有跨站分析（或已退出且未約定保留）就不排新分析、不產新向量、不把該站複本併進跨站分群。
- 刪複本才清分析摘要、向量、附件檔名與匯出副本。去掉 email／電話不是匿名化。
- 反悔：`cross_site_insight=0`、`retain_after_exit=0`；已寫入的洞察仍在，直到刪複本。
