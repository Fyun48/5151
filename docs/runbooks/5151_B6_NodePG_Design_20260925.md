## 0. 先修正目前完成度的判定

### 0.1 「30 秒中斷」不是已證實的 statement_timeout 或計畫原因

`Connection terminated unexpectedly` 證明連線非預期終止，不能單憑耗時就判定 PostgreSQL statement timeout。審閱版本 driver 的預設 `statement_timeout` 是 15 秒，實際環境可以覆寫；報告卻集中在 30 秒，應對照實際生效值與代理／client timeout。

已確認的程式結構是：builder 把 `p.source`、`p.area`、`p.kind_keys` 加進 `clauses`，再把整份 clauses 放入：

```sql
FROM listing_search_projection p
WHERE p.post_id IN (
  SELECT post_id FROM listings
  WHERE ... AND p.source IN (...) AND p.area <= ...
)
```

這使內層參照外層 `p`，是優先修正的可疑點。**尚未取得 EXPLAIN，不宣稱已證明它是 30 秒中斷的唯一原因。** `IN (SELECT ...)` 本身也不必然慢，不能把所有 IN 都機械式改成 JOIN。

先完成以下唯讀收證，不調整正式全域設定：

1. 留存實際送出的 SQL、參數型別、受控案例參數、程式 SHA、版本、`application_name`、`pg_backend_pid()`、連線端點類型與實際 `SHOW statement_timeout`。不要輸出憑證、私人搜尋字詞或會員筆記。
2. 先取 `EXPLAIN (VERBOSE, FORMAT JSON)`；再以診斷連線、短 timeout 跑 `EXPLAIN (ANALYZE, BUFFERS, SETTINGS, TIMING OFF, FORMAT JSON)` 的 SELECT。取消逾時的查詢，不反覆等待 30 秒。ANALYZE 逾時通常拿不到完成的實測 plan，保留估計 plan 與錯誤。
3. 在同一條專用連線使用 `BEGIN READ ONLY`／`SET LOCAL statement_timeout = '3s'`，必要時 `SET LOCAL lock_timeout = '500ms'`，結束後 ROLLBACK；這只限制該診斷交易，不修改正式服務設定。先確認工具確實固定同一個 client。
4. 依 backend PID／時間對照 PG 日誌、wait event／blockers、代理與容器日誌。`57014` 是 query canceled，不能和斷線混稱；也檢查重啟、OOM、網路及代理逾時。
5. 檢查既有索引定義與有效性、資料分布及 last_analyze／last_autoanalyze。需要 ANALYZE、建索引或修改統計資料的實驗，先在 CI／隔離副本做；目前正式環境只讀收證。

## 1. B6 最小設計：先 SQL 結構，再決定索引

### 1.1 先修條件位置

把 builder 分成 `listingPredicates` 與 `projectionPredicates`，各自帶參數，最後依 SQL 出現順序組合。最小修改是在既有 IN 結構中，把只用到 `p.*` 的條件移到外層；並以顯式 PK JOIN 當另一個計畫比較版本：

```sql
SELECT count(*) AS candidate_count
FROM listing_search_projection AS p
JOIN listings AS l ON l.post_id = p.post_id
WHERE /* listing predicates：全部明確使用 l／各自的別名 */
      /* projection predicates：使用 p */
      p.district = ANY($1::text[])
  AND p.source = ANY($2::text[])
  AND (p.area IS NULL OR p.area <= $3);
```

這只是結構示意，非完整可直接上線查詢。來源授權、個人旗標、fixture 隔離、display readiness 等原條件都要保留；一對多關係用 EXISTS／去重的鍵集合避免 JOIN 膨脹。不要靠最後 COUNT(DISTINCT) 掩蓋錯誤 JOIN。

**此時只能稱 candidate_count，不能稱最終 totalMatched。** 在 same-house／個人覆寫未進 SQL 前，最終 total 仍由完整 Node 管線產生。

### 1.2 最小欄位與索引選擇

| 能力 | 欄位決策 | 索引候選 |
|---|---|---|
| sources | 重用 `p.source TEXT`；這次不新增 source 維度表，也不為了索引更換成數字 ID | 單區常見查詢先比較 B-tree `(district, source, post_id)`；若 source=591 選中多數資料，索引未必有利 |
| areaMax | 重用 `p.area` 數值；維持 NULL 通過，保留原精度與邊界 | B-tree `(district, area, post_id)`；這是純量比較，不需要 range type／GiST |
| kind | 新增 `kind_tokens TEXT[]`（PG），由共用 canonical token 函式產生 | GIN `(kind_tokens)` 支援 `@>`／`&&`；先量測條件移正後的計畫，再決定是否部署 |
| wholeFloorOnly | 使用 canonical token `whole`；維持有 kind 時 skip 的契約 | 與 kind 共用 GIN；若分布與頻率證明值得，才考慮專門的 partial index |
| elevator／parking／low_floor／rooftop | 都已存在；不要再建立同義欄位 `has_elevator` | 不逐個 boolean 建索引；由常見組合及計畫證明複合／partial index 的價值 |

PG 的 `kind_tokens` 與 SQLite 的實體表示可不同；共用的是 token 產生與 query 語意，driver adapter 負責 SQL，不能因為追求字面上同一 SQL 又退回不可索引的字串掃描。

範例表達：

```sql
-- 必須具有某一 token
p.kind_tokens @> ARRAY['whole']::text[]

-- 一個類別集合中至少符合一項
p.kind_tokens && ARRAY['building', 'apartment_huaxia']::text[]
```

仍由 `kindsToQuery`／`effectiveAppearanceCategories`／`commercialCategories`／`elevatorRequired` 組合條件。**不能把全部勾選 token 一律 AND，也不能一律 OR。** `whole` 還可能搭配預設 appearance 規則；舊 suite／yafang 選項也要保留。

遷移期 `kind_tokens=NULL` 代表尚未建立，空陣列代表已建立但沒有 token，兩者不可混用。查詢必要範圍有未知／過期投影時，走精確 Node 路徑，不可靜默排除。

不新增所有索引組合。先在 12 萬列、帶偏斜分布的 fixture 上比較「修 SQL、無新索引」「加 B-tree」「加 GIN」，記錄寫入成本與索引大小。Seq Scan／Nested Loop 不一律判 FAIL；判斷實際處理量、loops、buffers 與耗時。大量命中的條件選 Seq Scan 可能合理。

partial index 必須有 query 可推導的固定條件；不要把 per-user hidden／split 放入全站 partial index。建索引後統計資料也需更新；若同表 district／source／類別有明顯相關且估計失真，再評估 extended statistics，不把它當 join 問題的萬用修復。

### 1.3 可索引不等於可提前過濾

Node 現行順序中，kind／sources／顯示條件在角色判斷之後。提早只取符合 kind／source 的房源，可能把決定 primary 的另一筆移掉，改變最終清單。

- B6 可先算 SQL predicate 的 match flag、縮窄已證明安全的前置範圍，讓 Node 在原階段套用。
- 做候選減量時保留必要關係上下文，包括反向指向與個人群組；但「為取得上下文展開關係」不等於「把整個連通分量合併成一個房源」。
- area 位於不同的 profile 階段，也要分 filter 驗證；不能把全套 filter 當相同流程。
- 未證明完整管線等價前，SQL 索引與述詞效能通過不代表可以恢復正式 sql_pg。

## 2. 角色比較輸入：需要設計完整，但不阻塞前述修復

**B6 的四項可索引表達，不必等角色欄位全部完成；要宣告完整 same-house SQL 搜尋，則仍需要這份契約。**

| 必要語意 | 最小儲存／取得方式 |
|---|---|
| identity／peer／verdict | 重用 PG listings 的 post_id、match_post_id、match_verdict；現有 `primary_listing_id` 只是 peer 的同義資料，不當 winner |
| comparableRent | 由同一 `comparableRent` 產生；可重用 `total_monthly_cost` 並把無效／非正數正規化為 NULL，先證明一致，包含額外月費 |
| refresh | 新增 `refresh_basis`＝absolute／relative、`refresh_value_ms`＝時間或 offset；查詢固定 `asOf`，relative 使用 `asOf-offset` |
| 平手比較 | 原始 last_seen_at 語意、共用 `listingTieBreakKey` 產物、數值 post_id；未證明 PG collation 等價前，tie-break 留 Node |
| readiness | PG 的 source enablement、listing_prep 與 offline；先 join／preload，不物化最終 per-user readiness |
| 新鮮度 | projection／comparator version 與可驗證的 input revision；`updated_at` 搜尋排序欄位不是通用資料版本 |

最小新增實體欄位可收斂為 `kind_tokens`、`refresh_basis`、`refresh_value_ms`、`tie_key`、版本欄位；其餘重用既有欄位／PG 關係。若 comparableRent 重用無法證明一致，才新增獨立 nullable 欄位。最終 `primary/affiliate` 不固定進共用投影。

回填策略：

1. 先抽出不 import `db.js` 的純計算模組；固定 `asOf`、決定配對候選順序，補相對時間與鏈／環 fixture。不得在本次效能修復偷偷改 primary 優先序。
2. 相容新增欄位，讓所有相關寫入端先持續維護新投影。凍結本輪 projection version 與欄位集合。
3. 同一支回填以 keyset 分批，從 PG canonical row 一次計算該版本全部衍生欄位；初始 batch 500，依交易時間／WAL／複寫落後調整。不要為了等 C 的額外欄位延後 SQL scope 與 provider 修復。
4. 防止舊快照覆寫新資料：有列 revision 就做 CAS；沒有時，在短交易鎖定、重新取得 canonical row 後計算更新。不可用無保證的時間戳或排序欄位替代 revision。
5. 失敗列有限次重試、留清單；可續跑、可重新驗證。資料筆數相等不代表欄位新鮮，需比 input version／衍生值。
6. 大批新欄位先回填、再評估建立索引和更新統計；正式 DDL／回填仍依手動維護流程準備。PITR 未啟用不阻塞程式／CI 工作，但這份設計不授權直接執行正式資料庫變更。

## 3. PG＋Node：先做哪一項優化

**優先序：資料來源正確 → 分階段批量 preload → closure 演算法 → 減少重算 → 必要時 worker pool。** 不限制候選筆數，不先把配對整段搬成未證明等價的 SQL，不另跑一次錯誤的 SQL total。

### 3.1 拆開計算所需與畫面所需資料

目前 `preloadDecorationProviderAsync` 原本是「一頁」的裝飾 loader，卻被傳入整批 raw 候選，會為未顯示的資料載入群組、MRT 等資訊。

- 候選階段：批量載入會影響入選、角色、排序的資料，包括 flags、split、personal groups、必要 peer／prep／來源設定。通勤若會影響篩選或排序，相關 route 資料仍須在此取得。
- 完整 Node 判斷後，一次得到存活列、排序、total 與 page IDs。
- 頁面階段：只替 page IDs 載入照片／大欄位與純展示的 MRT、job、peer 裝飾；不能延後會影響入選的依賴。
- 共用 request-scoped loader／memo。現在外層載 flags、preloader 內又新建 loader 重讀，closure 也會和 personalIndex 重讀會員群組。
- 群組載入改成一次以 group IDs 批量 JOIN，取代逐 gid `await groupMemberRows(gid)`。使用 typed array／有限分批，而不是每列查一次。
- 不用大量 Promise.all 淹沒連線池。同一 client 的 snapshot 查詢會序列執行；真正要省的是 round trip、資料量與重複讀取。

### 3.2 修 closure 的 CPU 退化，之後再減少全圖傳輸

目前 `districtClosureIds` 每次都取全站 match 邊，union-find 沒有 path compression／rank。以相同邏輯的鏈狀輸入計數：

| 節點數 | parent 走訪次數 |
|---:|---:|
| 1,000 | 999,000 |
| 2,000 | 3,998,000 |

這是合成最壞情境的複雜度證據，不能把正式站 262ms lag 全歸因於它。最小修復可加 path compression＋union-by-size；或使用 adjacency map＋visited BFS，保持 closure ID 集合一致，補長鏈、星狀、大群組、環狀案例。

下一步比較「只批量取得 reachable frontier」與合法的單一 recursive term PG closure。PG 支援 `WITH RECURSIVE`，原本多個 recursive 分支的寫法不合法，不代表此需求不能 SQL 化。若試驗 PG 版本，普通 CTE 先建立 edge 關係，recursive term 只參照一次 reachable；個人群組用星狀連邊避免生成 k² clique。必須以完整 plan 驗證，不能假設 CTE 一定快。

檢查／按缺項補索引：listings 的 PK、`(match_post_id, post_id)`；個人群組的 `(user_id, post_id)` 與 `(user_id, group_key, post_id)`；flags 的 `(user_id, post_id)`；split votes 的對應 user／pair 鍵。不要重複建立已等價的索引。

先避免每請求重算可重用的字串解析／JSON／cost／tie key，將純計算結果一次算好。若以上完成後仍有長時間同步區塊，再用固定大小 worker pool 執行完整純 Node 判斷；不能每次請求建立 worker，也不能讓 worker import 會初始化 SQLite 的 db.js。記錄資料複製成本、queue wait 與 worker 記憶體。I/O 不適合靠 worker 加速。

### 3.3 初始工程目標

基準 fixture：12 萬列，單區約 6,000～10,000 候選，page 80；warm pool；包含已登入使用者、配對與群組。一般查詢與通勤／fit 分開報。

| 指標 | 初始目標 |
|---|---|
| PG 請求裡的 SQLite I/O | **0** |
| 一般單區資料 SQL 次數 | **≤12／請求**；不含 BEGIN／SET／COMMIT，另列控制語句；頁面／群組數增加不應造成逐筆成長 |
| 通勤／fit 的資料 SQL 次數 | **≤16／請求**，以明列需要的批量 lookup 為準；大型 ID 分批另列原因 |
| 實際同級環境 node_pg 端到端 p95 | C=1 **≤1,000ms**；C=4 **≤2,000ms**；尚未量測，不當成保證 |
| 主執行緒 event-loop delay | steady-state p99 **≤50ms**，max **≤100ms**，另記最長同步 CPU 區塊 |
| 記憶體 | C=1 暖機後峰值增加先以 **≤64MiB** 為工程預算；C=4 另量整體峰值與容器餘裕，連續多批結束後不可持續無界成長 |

不要為了達到 SQL 次數目標刪掉必要資料；先讓資料集合正確，再量測。count 的 1 秒預算也不能套到整個請求後宣稱達標。其他整區／全區與重型通勤案例另有報告，不能拿單區結果概括。

## 4. 效能閘門：要進 CI，但分三層

### 4.1 先修 benchmark 本身

目前 `listingSearchNodePgPerf.mjs`：

- RUNS 預設 5，以 nearest-rank 算出的 p95 就是 max；不足以作穩定驗收。
- uid=0，沒有涵蓋真實會員 flags／personal groups；也沒傳 `searchKeys: []`。A/B 文件顯示「省略 searchKeys」與明傳空陣列曾得到 0 與 6,228 的不同結果。因此每份結果必須附有效 args／解析後範圍／候選數，確認量到同一個工作量。**不能把 searchKeys=[] 當正式漏資料的繞過修復。**
- `firstRunQueries` 寫在第一輪 last 物件，後續覆寫 last 會丟失；改成獨立變數。一般會員與 uid=0 分開量。
- RSS end-start 是整段程序的記憶體差，不是每請求用量，也不是峰值；記錄峰值 RSS／heap 與暖機後批次結果。
- 只統計包裝過的 PG query，沒有統計旁路 SQLite。把 SQLite I/O 次數一起納入 gate。
- `queryDetails` 逐階段輸出；固定一次 asOf／snapshot。冷連線建置與 warm pool 請求分開，不把新連線成本混進穩態 p95。

量測採暖機 5 次，正式每案至少 30 次，輸出原始分布與樣本數；接近門檻再加到 100 次。CPU／event-loop 的觀測窗口至少 30 秒，使用相同 resolution 並記錄 idle baseline。併發測試在 CI／隔離環境執行；正式只做低負載唯讀收證，不突然發動壓測。

### 4.2 Gate 分層與門檻

1. **每個 PR 的必要 gate：** GitHub-hosted Ubuntu＋PG service，明確 `PG_TEST_URL`、正式 migration、required PG 測試不可 skip；完整 parity、SQLite I/O=0、依賴未截斷、查詢次數無 N+1、timeout／斷線為 0。使用正常入口和完整 builder，禁止以空 stub 拿掉 district／visibility 後稱 E2E。
2. **PR 的固定規模 smoke：** 12 萬列合成 fixture＋偏斜來源／行政區／關係分布；ANALYZE 後取得 plans。每案 warm count／candidate SQL 的 client wall p95 **≤ min(1,000ms, T/3)**；同時列 server Execution Time。T 使用診斷／CI 固定的 3 秒上限，因此有效門檻是 1 秒，不得靠調大 timeout 放寬 gate。node_pg C=1 p95 起始 smoke 上限 **2 秒**。正確性與 timeout 失敗即 FAIL。
3. **較完整 benchmark／恢復 SQL 前 gate：** C=1／4 的全管線、記憶體、lag，必要時 C=8 作壓力觀察；依同級環境的上一節目標判定。Hosted runner 的時間結果和 NAS 分開記錄，不宣稱 CI 的 500ms 代表 NAS 也相同。另在同 job、同 fixture 交錯量目前正式 node_pg 基準與新版本；p95 超過基準 25% 且差超過 100ms 時產生 regression finding，第二個固定批次仍重現則 FAIL。不能使用已知錯誤的 sql_pg 當正確性或全管線速度基準。

對 hosted runner 噪音只允許預先定義的第二批確認，不無限重跑直到綠燈。單一 plan node 類型、索引名稱或 planner cost 不作硬性版本鎖定；把 JSON plan、buffers、rows、loops、bytes、query 次數和時間留成 artifact。

GitHub Actions 的 service container 足夠，不需要自架 runner 或正式 secrets。從 repository 根目錄 `npm ci`；`package.json` 在根目錄，測試目前為 `npm test`。使用與正式相容且已驗證版本的 Node／PG image（PG 16.14，固定實際 digest），測試 DB 叫 `5151_ci`；新增專用 perf script／測試命令後接 workflow。required PG 測試缺環境直接 FAIL，不能延續 20 個 skip。

## 5. sql_pg 是否保留

**保留 builder、repository、差分與 EXPLAIN 工具；移除正式 PG 請求可以選到 sql_pg 的入口。** 不是只把預設設成 node_pg，因為 baseline／q 都已量到約 40% 的 total 差異，並沒有一個可正常上線的剩餘能力。

- A/B 與 benchmark 直接從明確的診斷 script 呼叫 SQL repository，不能受會員 query string 控制。
- production 的 `PG_SEARCH_ENGINE=sql_pg` 不可繞過 gate；啟動檢查應給明確不支援錯誤，或由正式建置根本不提供該選項，不靜默用錯引擎。
- 既有 SQLite 開發／parity 路徑若仍共用 builder，不因移除 PG 正式入口而誤刪。
- 移除正式 catch 可達的 `options.sqliteFallback`；測試差分直接呼叫指定 adapter，不需要讓正式錯誤處理保留換庫能力。
- 將「可產生／執行的 SQL predicate」與「已核准回應使用者的完整搜尋能力」分開記錄，避免再次用單欄位 parity 宣稱整條搜尋等價。

## 6. 請 DeepSeek 一次接續完成的順序

1. 建立 PG service CI 與正常入口的最小 fixture；先讓 provider／LIMIT 8／SQLite I/O 的回歸案例確實失敗。
2. 修正 request context、provider 全鏈、flags 身分、peer／prep 完整性、固定快照／asOf／候選順序；移除正式 sql_pg 與 SQLite fallback 入口。
3. 拆候選 preload／頁面 decoration，共用 loader、批量群組，修 closure 的退化演算法，重跑正確性。
4. 修 SQL 的 p.* 作用域；用現有欄位比較計畫，確認 30 秒中斷原因，再實作 kind_tokens／選擇有證據的索引。
5. 如本輪已凍結比較輸入契約，一併準備版本化回填工具；先在隔離資料驗證 race／resume／失敗處理，不動正式設定或直接回填。
6. 跑分層 CI 與效能報告，更新 PR 本文（目前還保留多項舊完成度與 fallback 描述），回報 exact HEAD、同 SHA CI、差分、plans、資料來源 I/O、各階段時間與剩餘問題。程式、CI 與唯讀量測可持續完成，不因 PITR 尚未啟用停在設計階段；正式變更另走既有手動流程。
