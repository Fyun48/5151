# OPS 產品規劃（給 Owner）

這份是 OPS 的目標藍圖。程式骨架（Phase 1–15）已經在 `ops/src`，但**多數會動真錢、真程式、真正式機的開關預設是關的**。  
Owner 直接下令改 v3 並 Deploy，不必走這條線。

完整雙向敘事（可加入／可退出、每扇門都有出口、我依序要做的工作包）見 [`BLUEPRINT.md`](BLUEPRINT.md)。

## 你說的流程對不對

對，這就是設計中的主路徑：

```
各站使用者回饋
  → OPS 收件、分群、五角色評估（不是全民公投）
  → 建議「要做」時通知你（Gate #1）
  → 你按「核准開發」
  → 指定的製作 AI 在隔離工作區改程式、開草稿 PR
  → 自動 QA
  → 先上測試站給你看
  → 組好變更清單，再通知你（Gate #2）
  → 你同意才上該站正式機
  → 出問題或反悔：退回上一版已知良好的程式
```

現在缺的不是「再發明一條流程」，而是把關著的接頭接上，並讓 OPS 從「只服務 v3」變成「可掛多個站」。

| 關卡 | 設計有沒有 | 正式機現在能不能用 |
| --- | --- | --- |
| 回饋進 OPS、收件匣、議題 | 有 | Console 有；v3 遞送預設仍關 |
| 五角色評估 → 通知 Gate #1 | 有 | 要開評估／提案 provider + webhook |
| 你核准後 AI 開始做 | 有（Coding Provider） | **關。** Cursor 接頭標成尚未整合；預設不寫 repo |
| 測試站 | 有（Staging Provider） | **關。** 還沒有真的測試容器 |
| 你看變更後同意上正式機 | 有（Gate #2 + Phase 15） | **關。** 正式部署仍是你手動 Deploy v3 |
| 退回上一版 | 有（code rollback） | **關。** 且資料庫還原與程式退回要分開 |

「投票」是 OPS 裡五個角色（產品／工程／安全／合規／維運）的評估，不是使用者公投。使用者只負責回饋。

## 1. 製作的 AI：可以委任別人，後台開關金鑰

可以。製作端本來就該是**可插拔的供應商**，不是綁死「只有 Cursor 這一個對話」。

後台（只在 OPS，不進 v3）建議做成「供應商抽屜」：

| 抽屜 | 幹嘛 | 可選供應商（例） | 預設 |
| --- | --- | --- | --- |
| 分析 | 讀懂回饋 | stub／OpenAI／Anthropic／Gemini | 關 |
| 分群 | 同類回饋合成議題 | 同上（embedding） | 關 |
| 評估 | 五角色要不要做 | 同上 | 關 |
| 提案 | 寫給你看的變更說明 | 同上 | 關 |
| **製作** | 真的改程式 | Cursor Cloud Agent、Claude／Codex 類 agent、本機指令、或「只開 PR 等你指定的人做」 | **關** |
| 審查 | QA 的可選 AI 評語 | 同上 | 關 |

每個抽屜：

- **關閉**：那一關停住，前面的回饋照常進。不會假裝做完。
- **開啟**：你貼入該供應商的金鑰或授權，存在 OPS 資料目錄（不進 git、不進 v3 映像）。
- **可換**：同一個議題可以指定「這次用 A、下次用 B」。
- **範圍**：製作 AI 只能改該產品允許的路徑（例如 v3 只能動 `v3/`），不能改部署授權檔、不能 push `master`、不能自己合 PR。

對你「除了你，能不能委任別的 AI」的直接答案：

- **可以委任。** 這是 provider，不是寫死一個人。
- **現在還不能從 OPS 一鍵叫起 Cursor Cloud Agent。** 程式已留 `CODING_PROVIDER=cursor`，但標成尚未整合，避免發明不存在的 API。
- 在接頭完成前，實務上仍是：你 Gate #1 同意 → 通知你 → 由你在 Cursor（或你指定的 agent）做 → 開 `ai-dev/*` 草稿 PR。OPS 認的是 PR／測試結果，不是哪一個牌子的模型。
- 金鑰只放 OPS 後台。v3 正式站不要放製作金鑰。

## 2. 測試站誰來演？要不要再開容器？

要有一個**和正式站分開的執行環境**，否則你 Gate #2 看到的只是程式差異，不是「用起來長什麼樣」。

誰來演，由好到不好：

| 做法 | 建議 | 原因 |
| --- | --- | --- |
| NAS 上再一個容器 `591-tracker-v3-staging` | **首選** | 和正式站同一台、同一條 Tunnel 加 hostname（或只給你 Access）；資料 volume 分開；壞了不影響 c5151 |
| 每個任務開一個短暫容器、做完就拆 | 以後可做 | Phase 12 的理想；CasaOS 上比較煩，先不要 |
| 用現有 v2（b5151）當測試站 | 不要 | v2 是舊產品，不是 v3 的預覽 |
| 用正式站 c5151 當測試站 | 不要 | 測試等於上線 |
| 只用 Cloud Agent 的暫時虛擬機 | 不夠 | 機器會消失，你沒有穩定網址可以點 |
| 另開一個 GitHub 專案／第二條 Tunnel | 不要 | 違反本專案「同一 repo、同一條 Tunnel」 |

測試站規則：

- 埠例如 `127.0.0.1:5155`，公開 hostname 另開（例如 `jibbyrent-staging.reversalplay.me`），建議加 Cloudflare Access，只准你的信箱。
- **自己的空庫或脫敏複本**，禁止掛正式 `v3.db`。
- 憑證與正式站分開（不能用 NAS 正式部署 key）。
- OPS 的 Staging Provider 以後只對這個容器做「用某 SHA 換成測試映像／bind-mount」。
- 其它未來站台：每個產品一組「正式容器 + 測試容器」，不要共用測試庫。

所以：**要再開容器，但只要一個長期存在的測試容器（每站一台），不是再開一套 OPS、也不是再開一個 GitHub。**

## 3. 同意部署、自動上正式機、反悔與退回

你描述的就是 Gate #2 + Phase 15，而且應該維持：

1. 測試站通過、QA 綠、變更清單組好 → webhook 通知你。
2. 你在 OPS 看「改了哪些檔、對應哪個 SHA／映像 digest」。
3. 按同意 → OPS **只觸發已經存在、受保護的 Deploy v3**（workflow_dispatch、確認字串、只准 Owner 帳號），**不自己 SSH 進 NAS 亂改**。
4. 按不同意／退回提案 → 不上線，製作分支保留或關閉。
5. 已經上線才反悔：**退回上一版已知良好的映像 digest**（程式退回）。  
   資料庫還原是另一件事，可能丢掉上線後的新物件／新會員，預設不做自動還原；要還原必須另一次明確確認。

現在正式機 Phase 15 仍是 `PRODUCTION_RELEASE_ALLOW_LIVE=0`。在測試站與 Gate #2 畫面做穩之前，不應打開自動上正式機。

## 4. 多站監控：OPS 是控制台，不是 v3 的附件

OPS 應該是**產品中立的控制面**。v3 只是第一個加入的產品。

每個加入的站在 OPS 登記一張「產品卡」。**顯示名、目錄、workflow 名稱不能當安全識別。**

- 穩定 `product_id`（例如 `v3`、以後 `shop`）、經營者、來源實例
- 訂閱狀態與訂閱世代、功能權限
- 回饋 ingest 憑證（每站／每世代一把；伺服器用憑證決定 product，不信客戶自填）
- 各環境的 repo／workflow／container／資料位置／部署身分
- 顯示名、公開網址、測試網址、設計主題 id（只供人看）

Console 頂部加產品切換。收件匣／議題／稽核都帶產品標。總覽可看全部，也可只看一站。

新站加入 OPS 的最小條件：

1. 站內**自己先有**回饋表與站方後台可見（local-first，見第 8 節）
2. 能 HMAC POST 到 `/ops/api/ingest/feedback`（可關）
3. 在 OPS 登記產品卡
4. 有自己的正式容器與資料目錄
5. （可選）有測試容器，才准走自動 Gate #2

**不要為每個新站複製一套 OPS。** 也不要讓 v3 的物件資料庫跟其它站混在一起。  
**更不要讓任何站的回饋／CRM／會員資料「只活在 OPS」。** 否則分家拔線，對方站會殘廢。

## 5. UI／UX 模組化：可套主題，不是整站貼上

「v3 很好看，以後別的站只改配色」——**按鈕、表單、導覽、狀態可以這樣做；找房卡片、許願房不行整包貼到完全不同的產業。**

分三層，才不會把租屋資訊架構焊死進每一個站：

```
① 基礎 token     顏色／字級／間距／圓角／陰影
② 共用元件       按鈕、輸入、分頁、表格、底欄、對話框、空狀態、錯誤
③ 產品區塊       物件卡、比較列、關注配額……只屬於該站
```

| 層 | 現在 | 以後 |
| --- | --- | --- |
| ① | 已抽成 `design-system/tokens.css`；v3 仍保留內建 `tokens.css` | 每站一個主題檔只覆寫 `--accent`、`--bg`、`--paper` |
| ② | 已抽 `design-system/components.css`（`.ds-*`）；OPS Console 吃同一套 token 名 | 找房卡片不要整包貼到別的產業 |
| ③ | `design-system/property-platform/` | 繼續只服務吉比租房；新站另開 `design-system/<產品>/` |

新站啟動清單：

1. 複製主題檔，只改配色與商標。
2. 套用共用元件（登入、表單、底欄、回饋鈕）。
3. 只做該站獨有的區塊。
4. 在 OPS 登記產品卡，回饋鈕指向同一套 ingest。

這樣 OPS 監控的是「各站的回饋與發布」，設計系統管的是「各站長得像一家人」。兩件事分開，才能多站、又不用把 OPS 做成網站產生器。

## 6. 建議實作順序（依 2026-09-10 審查調整）

完整契約與每包驗收見 [`BLUEPRINT.md`](BLUEPRINT.md)；現況對照見 [`INVENTORY.md`](INVENTORY.md)。順序已改成「先身分與退出，再 CRM 與自動部署」：

0. **修訂藍圖與現況清單** — 本檔／BLUEPRINT／INVENTORY／外掛規格對齊審查。
1. **多站資料／權限模型＋獨立站契約** — A、B 不撞號、不串資料；各站可關閉 OPS。
2. **OPS 自身可重現部署與產品卡** — 只部署 OPS，不變成 v3 的第四條路徑。
3. **訂閱／退出／移交最小演練** — 一個範例站在沒有 OPS 的乾淨環境還原。
4. **站內 CRM → OPS CRM 檢視** — 先有可獨立操作的站方資料；關 CRM ≠ DROP。
5. **隔離 staging＋任務／發行 UI** — 已發布事實不變；再開發用 follow-up。
6. **OPS 供應商與 v3 BudgetGuard** — 先保留額度才呼叫；並行不超支。
7. **pHash、同屋源 AI、爬蟲資料 AI** — 附屬表、分開開關、不鏈式合併。
8. **OPS live 串接既有部署** — 多站目標、Owner 指令來源、完整退回。Owner 直達線現在就保留。
9. **共用設計元件** — 固定版本、可打包；runtime 不回抓 OPS。
10. **遠端客服操作** — 預設關；OPS 下令、本站驗證寫入、離線不假成功。
11. **跨站洞察與清除** — 預設關；回饋複製不含跨站分析；撤回／退出停新洞察；刪複本才清向量與匯出副本。
12. **統計指標與後續服務門** — 預設關；回饋複製不含這兩項；未授權站不列入未標站指標；入庫 webhook 要後續服務；清除帳本還原後重套。不發明報表或行銷流程。
13. **Worker 重驗訂閱世代** — 分析／分群在外部呼叫與寫入前重驗世代與授權；晚到結果不開單、不寫入、不復活已退出訂閱。
14. **晚到評估／提案／webhook** — 評估、提案與入庫通知在寫入或外送前重驗世代；未綁 product 的舊議題維持相容。不重做製作整條線。
15. **製作／QA 重驗訂閱世代** — 能推到產品的製作與 QA 工作戳上世代；claim／complete／開 PR 前重驗。未綁產品的任務仍列出但不能宣稱已撤回外部呼叫。不接真 Cursor、不開 live。
16. **staging／發行重驗訂閱世代** — 隔離 staging、發行候選、發布通知與正式發布在外送／寫入前重驗世代。未綁產品仍相容。不開 live、不合 master。
17. **移交前確認正式部署狀態** — 正式部署狀態不明時拒絕移交；未決清單標明須先確認實際結果。已送出的部署不宣稱撤回。不開 live。
18. **自動重評重驗訂閱世代** — 自動重評在重開議題前重驗世代；解除訂閱或換世代後不把舊議題救活。未綁產品仍相容。Owner 手動重評不在此限。不開 live、不合 master。
19. **遠端客服重驗訂閱世代** — 遠端客服命令戳世代；外送前重驗。解除訂閱或換世代後舊佇列不外送。未決清單列出。不開 live、不合 master。
20. **測試中的 QA 取消** — 見 BLUEPRINT 第 20 包。
21. **未送出的遠端客服可取消** — 見 BLUEPRINT 第 21 包。
22. **未送出的分析／評估／提案可取消** — 見 BLUEPRINT 第 22 包。
23. **未送出的發布通知可取消** — 見 BLUEPRINT 第 23 包。
24. **未決清單可取消製作／QA／staging** — 見 BLUEPRINT 第 24 包。
25. **未送出的正式發布可取消** — 見 BLUEPRINT 第 25 包。
26. **已受理正式發布的觀察與取消 runner** — 未決清單顯示執行中或已知結果；可取消尚未結束的 GitHub runner，不改寫正式終態、不宣稱撤回部署。程式退回與 DB 還原仍是不同操作。不開 live、不合 master。
27. **目前正式版可程式退回** — 已成功且為目前正式版的發布可從未決清單送程式退回；必須回傳上一版身分，不猜 latest。這不是取消 runner，也不執行 DB 還原。不開 live、不合 master。

每一步都要能單獨上線、單獨關閉。任何一步都不准讓「合進 master」直接部署正式站。

## 8. 分家退出：對方站還能不能用？

**可以，而且必須可以。** 前提是每個公開站都遵守「本機為主、OPS 為訂閱」。

以現在的 v3 為準（已經是這個模型，不是以後才發明）：

| 資料 | 寫在哪 | 退出 OPS 之後 |
| --- | --- | --- |
| 物件、會員、刊登 | 該站 `v3.db` | 不受影響 |
| 使用者「意見／回饋」 | **先寫進該站 `feedback` 表**；後台「使用者回饋」已可看 | 表單與後台繼續用 |
| 送到 OPS 的複本 | 僅當 `OPS_FEEDBACK_DELIVERY=1` | 關掉遞送、撤銷 ingest 密鑰即可；**站不會壞** |
| 議題、評估、Gate、稽核 | 只在 OPS | 對方本來就不該靠這些才能營業 |

所以：不是「退出後要把回饋自動改成預設留言板」——**預設本來就該是本機收件匣**。加入 OPS 只是多抄一份給你做產品決策與跨站分析。

退出請拆成四種動作，不要做成一個「退出」按鈕包辦搬家：

| 動作 | 效果 |
| --- | --- |
| 暫停某項功能 | 停 AI／指標等；本機營業繼續 |
| 解除 OPS 訂閱 | 本站停送、撤銷憑證；站留在原代管環境也可以 |
| 移交整站 | 可驗證的交接包＋唯一寫入端切換（第 3 包） |
| 刪除 OPS 複本 | 清明列範圍的複本；本站主本保留 |

第 1 包先做到：本機後台「停止傳送至 OPS」（不依賴 OPS 在線）＋ OPS 可暫停／撤銷該站憑證。完整移交與清除是第 3 包。

若某站是「幫別家做、對方在營利」：**從第一天就該 local-first**。你的 OPS 只訂閱複本。這樣分家是撤訂閱，不是拆引擎。

## 9. OPS 要不要加 CRM？

可以加，但是**模組，不是把各站會員搬進 OPS 當唯一客戶檔**。

兩層：

| 層 | 給誰用 | 資料在哪 | 分家 |
| --- | --- | --- | --- |
| **站內 CRM（可選套件）** | 該站經營者（含你幫別家做的站） | 該站自己的 DB | 跟著站走，退出 OPS 仍在 |
| **OPS CRM（控制台）** | 只有你 | `ops.db` 裡依產品分匣的複本／線索 | 退出時匯出給對方，然後停用或清除 |

OPS CRM 適合做的：

- 跨站線索：哪一站回饋最多、哪類需求重複（供你做下一個服務）
- 你自己幾個站的會員／贊助／後續聯繫（你經營的站）
- 與議題、發布紀錄掛勾（這個客戶的抱怨已變成哪張提案）

OPS CRM **不准**做的：

- 當別家公司唯一的客戶名單、訂單、發票
- 沒有對方同意就把他們會員個資拿去訓練或做你的下一項產品
- 退出後仍能從你的 OPS 後台寫回對方正式站

抓「可用資料做下一個服務」的合法範圍：

- 預設：只留聚合統計與去識別主題（「三人以上提到想要地圖篩選」）
- 要留可識別資料：產品卡上單獨勾選，且退出時必須能一鍵刪除或匯出給對方
- 爬蟲物件、公開刊登不是 CRM；那是各站自己的內容庫，退出後仍在該站

CRM 與回饋一樣：**站死不了，只是少一個遠端抄寫員。**

## 10. 和 v3 外掛／熔斷計畫的關係

租屋站要接 ZenRows、代理、Qwen、距離 API、預算硬熔斷——那是 **v3 自己的後台與自己的 DB**，寫在 [`../v3/PLAN-integrations.md`](../v3/PLAN-integrations.md)。

- 金鑰與每日預算活在 `v3.db`，不進 OPS。
- 沒開外掛或熔斷後，自動回到現有免費爬蟲／Haversine／現有同源規則。
- 關掉 OPS 或把 v3 退出 OPS，**外掛與爬蟲照常**。
- OPS 最多以後訂閱「今日花費／熔斷次數」這種營運指標，不當帳單系統。
