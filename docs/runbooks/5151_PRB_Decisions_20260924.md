# PR-B 決策回覆：same-house 語意、PG CI 與 PITR

日期：2026-09-24。交付對象：DeepSeek／5151 Owner。

審閱基準：PR #497，commit `9e621b95b5244e7f7524a0576d119dcdb0ed68c5`。本次完成原始碼與文件審閱，以及抽離現有函式的兩項小型重現；沒有登入 NAS 重跑生產量測、執行完整 CI、修改 repository 或操作正式服務。下列方案可供實作與修訂 runbook；實際部署與維護時刻另依 Owner 既有流程安排。

## 1) 選定方案＋理由

**先做 B，但資料全部來自 PG；接著做修正版 C，投影保存共用比較輸入，最終角色在查詢時決定。** 理由：現行角色同時依賴使用者、候選集合、配對順序與查詢時間，不能直接固化成全站通用的 primary／affiliate。

- 不採 D；不以近似 primary 規則冒充等價。
- 不把完整 A 當作緊急修復的起點。C 後續仍需要精確的查詢邏輯；新增投影欄位不會自動解決配對語意。
- 未證明等價的條件留在 PG＋Node 路徑。可分批恢復 SQL 快速路徑，不必等所有查詢都 SQL 化才修正已上線的錯誤。

### 本次核對新增的五個關鍵事實

1. **4,259／6,023 是 SQLite 快照上的兩條管線比較。** `pr-b-sql-node-divergence-measured-20260924.md` 明寫使用生產 SQLite `/data/v3.db` 唯讀量測。這是有價值的語意反例，但不能稱作「生產 PG 第一頁已有 30% 重複」的直接測量；正式 PG 的實際影響須另外量測。
2. **不只有 per-user split。** `attachSameHouseRoles` 的後半段會按使用者自己的同屋源群組重算並覆寫角色。全站共用角色加 split 例外，仍不完整。
3. **現有 `primary_listing_id` 不是已選出的 primary。** `computeListingProjection` 實作是 `Number(row.match_post_id) || 0`，只是 peer 指標，不能拿欄位名稱當語意證明。
4. **角色會隨時間改變。** 現有 `listingRefreshAt(row, now)` 以查詢當下解讀「1 小時前」。同租金兩筆：A 為「1 小時前」、B 為固定 `2026-09-24T12:00:00Z`；12:30 比較 B 勝，13:30 比較 A 勝。這是以現有 `preferPrimaryListing` 重現的結果。回填一次絕對時間會改變現在的行為。若要改成以抓取時間解讀相對字串，應作為另一項語意修正，不混入本次等價移植。
5. **候選順序也會影響結果。** 將現有 `attachSameHouseRoles` 抽離，以全數 display-ready、無個人群組／split 的 provider 測試：A→B→C、月費 3000／2000／1000；順序 A,B,C 留下 B,C，順序 B,A,C 只留下 C。原因是已有角色不再覆寫。這證明鏈狀配對的現行結果並不只由單筆投影決定；不表示已證實正式資料含此反例。

先讓共用 Node 參考管線固定一次 `asOf`，並在配對階段使用明訂的候選順序，例如數值 `post_id ASC`。這項確定化應獨立留 fixture 與變更說明，避免把 SQLite 偶然的列順序當成業務規格。**不要順便將所有 match 邊做傳遞合併**；A 與 B 配對、B 與 C 配對，不自動授權把三筆當成一個群組。複雜配對在規則與測試完成前維持 PG＋Node。

## 2) 對第 2～5 題的決定

### 第 2 題：驗收方向同意，原標準不足

`sqlOnlyCount=0` 與 `totalMatched` 相等只能當必要條件，不能作完整驗收。至少要求：

1. 在同一份固定 PG fixture／一致快照、同一使用者與設定、同一 `asOf` 下，完整結果的 `SQL − Node` 與 `Node − SQL` 都為空；不是只比較第一頁。
2. 排序後完整 ID 序列、每一頁邊界、重複 ID、`totalMatched`、`hasMore` 與分頁續接行為一致。最後一頁、空頁、不同 limit／offset 都要覆蓋。
3. 卡片上的角色、primary ID、primary offline、split／personal 標記及展開同屋源資料一致；只比 ID 會漏掉 UI 行為不同。
4. 驗證 pair 與 personal group；單向配對、反向指向、鏈／環、orphan、peer 在候選集合外或頁面外、主卡 offline、prep 未就緒、來源關閉、split、兩個使用者不同合併／拆分、租金缺失、含額外月費、完全平手、Unicode tie key、相對時間跨越絕對時間。
5. 所有 filter 與 source／district／kind／q／price 的組合，均以完整正式管線驗證。先前單一述詞等價的證據仍有用，但不能證明把篩選移到配對之前也等價。

`hidden`／`watched` 在 `listingIsMainListAffiliate` 中有例外；online affiliate 在 primary offline 時也有例外。不能一律 `WHERE role <> 'affiliate'`。`watched` 保留獨立的管理清單行為，不可套用一般瀏覽的行政區／價格／顯示條件。

測試分兩層：同一 fixture 在 SQLite／PG 的資料契約 parity；同一 PG fixture 在 Node／SQL 的查詢管線 parity。不要把仍會變動且時間不同的 SQLite 快照、正式 PG 當成等價 oracle。

### 第 3 題：同意先 B，必須是 PG-fed Node

建立明確的 `searchListingsNodePg` 能力（名稱可調整）：

- 從 PG 取得候選列、所需 peer、personal groups、split votes、個人旗標、listing_prep 與來源啟用設定；使用同一個一致快照。provider 資料缺少時不得暗中讀 SQLite。
- 共用純 Node 業務函式，依參考管線的先後順序完成配對、個人覆寫、篩選、排序、計數後，才取頁面。不得先 SQL `LIMIT 300` 再去 affiliate，也不得以任意候選上限截斷 total。
- 先量測實際最重的查詢與並行請求：p95、RSS、event-loop lag、PG 查詢數。用必要欄位與批量 preload 控制成本；若必須分批處理，仍需保留完整配對上下文與一致快照。分批讀取本身不會解決 CPU 阻塞。
- 若設定降級開關，只允許 `sql_pg`／`node_pg`，不允許切換資料來源。PG 連線／必要查詢失敗仍回 503 與既有穩定錯誤碼。

**不能直接開回既有 `listListings` 或 `searchListingsSqlite`。** 在審閱 commit，`listingSearchAsync.js` 仍有 `if (!page) return searchListingsSqlite(args)`，catch 也接受 `options.sqliteFallback === true`。所以「PG 錯誤預設不回 SQLite」不等於「所有 PG 查詢都不讀 SQLite」。把 unsupported-query 分支導向新的 PG＋Node；測試專用 SQLite 選項不得成為正式入口可達的逃生門。

### 第 4 題：採 GitHub-hosted Linux runner＋PostgreSQL service container

- 用與正式環境相符的 PostgreSQL 16.14 image／固定 digest，執行時驗證實際版本；在健康檢查成功後執行 migration、fixture 與 PG 測試。使用 repository 所讀的 **`PG_TEST_URL`**。
- 資料庫命名 `5151_ci` 等明確測試名稱。**`5151_shadow` 現在是正式 DB，禁止出現在可直接複製執行的 CI 範例中。** 隨機 schema 不能把正式 DB 變成測試環境。
- service container 每次建立／銷毀，只含合成或去識別 fixture；其一次性測試帳密可放 workflow，不需 GitHub Secrets。
- **允許 Secrets 保存隔離測試 DB 的憑證**；這不是本方案的必要條件。不得使用正式 PG／NAS 憑證，也不為讀取 secrets 改用能執行不可信 PR 程式碼的危險工作流程。
- 新增必跑 PG 測試模式：缺 `PG_TEST_URL`、PG 不可連、migration 失敗或列為 required 的 PG 測試被 skip，一律 CI 失敗。檢查具名測試清單，不把目前「20 個」寫成永不變的總數。
- 若 required 測試包括 standby／唯讀複寫行為，另建隔離的 primary＋standby job；**單一 PG service 不能證明 HA，`PG_TEST_STANDBY_URL` 也不能指回同一 primary 冒充。** 不因此引入可連正式 NAS 的自架 runner。
- 舊 master 同樣失敗只能證明不一定由本 PR 引入，不能單憑此宣稱是環境問題；保留失敗輸出並修正測試環境／依賴。必要 gate 未通過就維持 FAIL。

### 第 5 題：PITR 採 pgBackRest、每日 full、14 天可還原窗口

以下是規劃基準，不是已存在的配置：

- Repository 放在與 PGDATA 分離的備份 volume，優先不同 NAS；兩個 PG 節點都必須能在自己成為 primary 時封存。若只放在兩台中的其中一台，該台故障時備份庫也可能不可達，必須測試此情況與告警；後續另加獨立／異地副本。
- 目錄設計為 `<經實機驗證的備份掛載點>/5151/pgbackrest`。本次沒有該 volume 的掛載與容量證據，不能替 Owner 把 `/volume1/...` 範例宣布為已核准實體路徑。
- 初始排程採每日 full＋連續 WAL，**14 天可還原窗口**。pgBackRest 設 time-based full retention 14 天，讓工具一起保留窗口起點所需 base backup 與連續 WAL。不要 cron 按 WAL 檔案 mtime 自行刪除。新系統的覆蓋期從第一份有效備份鏈開始，不能立即宣稱已能回到 14 天前。
- 以整個 PostgreSQL cluster 的 physical backup 大小與實測每日 WAL 量估容量；549 MB 是單一 DB，當前 `pg_wal` 80 MB 也不是一天的封存量。回填負載、段切換與壓縮後的實際量都要計入。
- `archive_timeout=60s` 可作起始設定，但不是「RPO 保證 ≤60 秒」。還有封存傳輸／失敗延遲，且它不會把 async standby 改成同步複寫。
- 兩節點配置 `archive_mode=on` 與可工作的封存工具，讓 promoted primary 繼續封存；不要未驗證就使用 `always` 造成 standby 重複封存設計問題。具體 pgBackRest topology、版本與 repo 連通性列入 runbook。

**現有 PITR runbook 不宜照貼執行，先修以下缺陷：**

1. `test ! -f target && cp source target` 遇既有檔案會回傳非零，並非文件宣稱的成功；普通 `cp` 也不構成原子、耐中斷、可驗證持久化的封存協定。既有檔案只有內容一致且已可靠保存才可視為成功；不同內容必須拒絕。採 pgBackRest 處理，勿以 `|| true` 消音。
2. 刪除「封存成本可忽略」「重啟一定秒級」「60 秒 RPO 上界」等未驗證承諾。
3. 還原演練不能只查 `COUNT(*)`。用目標時間前後的已知交易標記，證明前者存在、後者不存在；記錄 recovery target、timeline、實測還原時間。還原實例應隔離於正式流量與封存目的地，避免複製原設定後再次寫入正式 repository。可安排工具支援的停止／pause 驗證流程。
4. 不用固定歷史時間當 target；target 必須位於 base backup 可還原的時間及已封存 WAL 範圍內。若沿用 tar-format `pg_basebackup -X stream`，必須正確處理 WAL tar、tablespaces 等完整備份內容；只解 `base.tar.gz` 不能直接當通用完整還原操作書。
5. 回退不可寫成「已封存 WAL 可人工清除」。保留既有備份鏈；若停封存造成連續性缺口，恢復後重新建立並驗證有效鏈，不能延續宣稱原 PITR 範圍完整。

**窗口原則可行，先預留 30 分鐘低流量維護時段，實際停機長度以演練為準。** 先完成掛載／容量／權限與配置檢查，先處理 standby 並確認重新追上，再在受控窗口處理 primary；不要同時重啟兩台。確認 HAProxy 與真正的 promotion 機制如何處理維護，不能把流量路由當成資料庫提升或 fencing。需要時 drain 應用與 crawler，給使用者明確維護狀態；不要為開啟封存額外冒險做一次無準備的 async failover。

runbook 提交實際主機、容器／服務命令、掛載點、容量、回復步驟與 UTC／當地時間後，由 Owner 決定實際窗口。這項準備可與 PR-B 修復並行，應用修復與 PG 重啟分開變更。

## 3) 修正版 C：投影欄位的最小設計

**存共用比較資料，並沿用 PG 中既有關係表；不新增「永久最終角色」作權威欄位。** 以下是語意欄位集合，既有欄位可直接 reuse／join，不要求重複存一份。

| 資料 | 最小表示／用途 |
|---|---|
| 身分與配對 | `post_id`、`peer_post_id`、`match_verdict`；可直接讀既有 PG listings。既有 `primary_listing_id` 必須註明／遷移為 peer 語意，不當 winner。建立反向 peer 查詢索引。 |
| 比較月費 | 共用 `comparableRent` 的 nullable 數值；既有 `total_monthly_cost` 可在驗證後正規化重用，因為本比較包含額外月費，不能只拿 `rent`。保留「未知不能贏過有效月費」規則。 |
| 更新時間 | `refresh_basis`＝absolute／relative、`refresh_value_ms`＝絕對時間或 offset；解析不到時沿用 `last_seen_at`／0 fallback。由共用 parser 產生；查詢固定 `asOf`，relative 才計算 `asOf − offset`。不可回填一次 `listingRefreshAt(row)` 就永久保存。 |
| 後續 tie-break | `last_seen_at` 的原語意輸入、共用 `listingTieBreakKey` 產物、post_id。Node `localeCompare` 與 PG collation 未證明等價前，平手／複雜情況留 PG＋Node；不要假設 timestamp DESC 或字元順序與現有函式相同。 |
| 顯示依賴 | peer 的 `offline`、`source`、`listing_prep` 必要狀態；來源 enablement 在查詢時從 PG 配置套用。若物化 readiness，必須有對應 dependency version 與失效機制。 |
| 新鮮度／版本 | `projection_version`、可比較的 listing／prep input revision。數值須來自明確的 revision 契約，不把隨機 hash 當可排序新舊版本。缺欄位／版本落後表示需 PG＋Node，不能默認「可見」或「不可見」。 |

個人 split、personal group membership、個人旗標留在按 `user_id` 隔離的 PG 關係資料，查詢時套用。若快取有效角色，key 必須涵蓋 user、設定／關係版本、候選語意與時間有效性；第一版不值得先引入這類快取。

實作順序：

1. 抽共用純函式、固定一次 `asOf`、明訂配對候選順序，建立前述 fixtures；參考管線必須先可重現。
2. 新欄位採相容新增；先讓所有 listing／prep 變更維護正確投影與 revision，再回填。必須考慮 peer 變動、改配對、刪除與來源開關對判斷的影響。
3. 回填分短交易、可續跑。以 revision 條件／鎖定重新取值等方式防止舊快照覆寫新投影，避免順便覆寫不屬於本回填的欄位。確定性失敗列須有限次重試、留失敗清單，不能無限重新挑選同一 missing row。
4. 現有 backfill 的 SELECT 雖分 batch，寫入仍逐列呼叫；70 分鐘是當前工具的量測，不是新增欄位的必然成本。先量測批量 UPSERT／staging 的小批次方案；不關閉 durability，也不承諾未量測速度。
5. 在同一 PG 資料上做完整雙向差分，逐項開放證明等價的 SQL capability。對 input revision 已過期、個人群組或複雜配對尚不支援的情況，維持 PG＋Node。

## 4) B 的緊急回退觸發條件

**現在已符合觸發條件：既有反例證明未完成同屋源語意的 SQL-first 不等價。不要等更多客訴或達到某個差異百分比。**

1. 優先停用所有尚未通過完整管線 parity 的 SQL-first 入口，導向已驗證的 PG＋Node。若無可靠的 capability 分流，先停用整條快速路徑。這項停用要與 PG＋Node 實作及效能檢查一起交付，不能只翻舊 SQLite fallback 開關。
2. 後續任何可重現的雙向 ID 差異、排序／分頁／total／角色差異，立即撤回相關 capability。測量需在固定資料與時間下完成，先排除兩次 live 查詢的合法資料更新差異。
3. 投影缺漏／過期、未支援的 personal group／split／filter／sort／設定，一律在規劃查詢時選 PG＋Node；不是捕捉任意錯誤後盲目重跑以加重資料庫壓力。
4. 不能只看目前頁的 `match_post_id` 是否非空。另一筆可能反向指向它，或它屬於個人群組；完整相關資料與依賴才是判斷範圍。
5. **PG 不可用、無法可靠取得必要資料：503。** 不使用節點 SQLite，也不回 200＋空列表／截斷 total 假裝成功。
6. 重新啟用 SQL 的條件是：版本與回填有效、具名 PG CI 必跑、完整 parity 通過、真實規模效能可接受；按已驗證能力逐步恢復並記錄 engine／原因／projection version 等診斷資訊，不記錄私人搜尋內容。
